# 2026-05-01 PDF规则提取技术报告大纲

## 1. 报告定位

本报告面向团队留档和后续复用，重点回答以下问题：

- 本项目如何从 PDF 文档中识别、提取并整理规则
- 一条规则如何从原始文本转化为结构化记录
- 提取结果如何经过审计、收敛、核对和 JSON 落库
- 当前方案中哪些步骤可以自动化，哪些步骤仍需人工判断

本报告不以“汇报展示”为主，而以“可理解、可复用、可追溯”为主。

## 2. 建议章节结构

### 2.1 项目背景与目标

建议说明：

- 项目的业务背景
- 为什么需要从 PDF 中抽取规则
- 本阶段的目标不是全文数字化，而是提取可交付的结构化规则

写作重点：

- 讲清楚“规则提取”的对象和边界
- 区分“原始文档”与“结构化规则库”

### 2.2 输入资料与规则定义

建议说明：

- 本项目使用的 PDF 文档类型
- 哪类文本被视为可提取规则
- 一条规则至少包含哪些关键信息

写作重点：

- 给出“规则单元”的定义
- 说明规则编号、规则名称、所属大类、所属小项、来源文件、来源页码等字段的作用

### 2.3 PDF规则提取流程

建议说明：

- 如何阅读原始 PDF 并识别候选规则
- 如何从原文中抽出规则内容
- 如何将候选规则写入主总表

写作重点：

- 突出这一步是“按统一口径进行人工识别和整理”
- 不要写成已经实现了全文自动抽取

### 2.4 规则拆分、归类与命名原则

建议说明：

- 什么情况下原文可直接形成一条规则
- 什么情况下需要拆分为多条规则
- 什么情况下同一原文可能服务于不同规则类别
- 如何处理重名规则和跨类别复用规则

写作重点：

- 解释“同源复用”和“真重复”的区别
- 说明命名澄清、口径判定和人工复判的必要性

### 2.5 审计、收敛与追溯机制

建议说明：

- 原始逐项审计的作用
- 二次收敛的作用
- 终版审计与规则追溯核对的作用

写作重点：

- 说明项目不是一次提取后直接交付
- 强调结果是经过多轮校核形成的

### 2.6 规则结构化与 JSON 映射

建议说明：

- 主总表中的规则如何映射到 JSON 模板
- 当前为什么采用按大类拆分维护
- 聚合 JSON 和分类 JSON 各自承担什么角色

写作重点：

- 讲清楚从“自然语言规则”到“结构化规则对象”的转换关系
- 说明 JSON 不是额外成果，而是规则库的结构化表达

### 2.7 半自动化核验方案

建议说明：

- 当前已自动化的内容有哪些
- 自动化脚本如何辅助规则库维护
- 自动化报告如何支持人工复核

写作重点：

- 定位成“半自动化核验”，不是“全自动提取”
- 明确自动化负责闭环检查、异常扫描和重复风险提示

### 2.8 当前成果、问题与局限

建议说明：

- 当前正式链路的成果规模
- 已解决的典型问题
- 仍需人工判断的事项
- 当前方案的边界和局限

写作重点：

- 用事实说明结果成熟度
- 保留对未决问题和人工依赖的真实描述

### 2.9 可复用流程与后续优化建议

建议说明：

- 后续如果继续提取新的 PDF，应如何沿用现有流程
- 当前哪些部分适合继续自动化
- 后续可优先优化哪些环节

写作重点：

- 用“流程复用”收口
- 给后续团队留下可执行的延续路径

## 3. 推荐写法

建议采用“项目实际做法为主，方法沉淀为辅”的写法：

- 前半部分重点说明本项目是如何完成的
- 后半部分再总结哪些做法可以沉淀为通用流程

建议整体按约 `7:3` 配比：

- `70%` 写本项目实际技术路线
- `30%` 写可复用的方法总结和后续建议

## 4. 建议附录

如果后续需要补完整技术报告，建议附录可包含：

- 字段定义表
- 规则 JSON 样例
- 核验脚本说明
- 重复规则判定示例
- 文件链路示意图

建议按以下顺序继续推进正文：

1. 先写“项目背景与目标”
2. 再写“输入资料与规则定义”
3. 再写“PDF规则提取流程”
4. 再写“审计、收敛与追溯机制”
5. 最后补“半自动化核验”“局限”“后续建议”
