# 2026-05-01 PDF规则提取技术报告

版本状态：正文初稿（已完成第 1-3 章）

## 1. 项目背景与目标

本项目的核心任务，是将炼化相关 PDF 文档中的操作要求、流程约束、质量标准等内容，整理为可交付、可维护、可追溯的结构化规则库。这里所说的“规则”，并不是对原始 PDF 全文做简单摘录，也不是对整份文档做普通文本电子化，而是从原始资料中识别出具有明确约束意义、可独立表达、可映射为结构化字段的规则单元，并将其纳入统一口径下的规则管理链路。

之所以需要开展这项工作，原因主要有三点。第一，原始 PDF 文档以自然语言叙述为主，内容分散在不同装置、不同章节和不同页码中，不利于后续统一检索、复核和复用。第二，业务上需要形成一份可以稳定交付的规则成果，而不是停留在原文阅读和人工经验层面。第三，后续还需要将规则进一步整理为 JSON 结构，用于规则库维护、其它 agent 接入或后续系统化使用，因此必须先完成从自然语言到结构化规则的转换。

结合当前项目实际，本阶段目标并不是实现“PDF 到规则库”的全自动提取，而是建立一条稳定的半自动化处理链路。该链路以前期人工识别和规则整理为基础，以逐项审计、二次收敛、终版核对和 JSON 映射为控制手段，再辅以自动化脚本完成结构一致性核验和重复风险提示。截止 2026 年 4 月 30 日，当前正式链路已稳定形成 215 条规则，并完成主总表、终版审计表与 JSON 规则库之间的一致性闭环。

## 2. 输入资料与规则定义

本项目的输入资料，主要是炼化相关的 PDF 文档和操作规程类文档。这些资料是规则提取的原始依据，也是后续追溯时的唯一上游来源。正式处理过程中，原始 PDF 并不直接作为最终交付成果，而是先进入人工识别、摘录、归类和记录阶段，再逐步转化为规则总表、审计表和 JSON 规则库。

在本项目中，一条“规则”应满足以下基本条件：一是文本中存在明确的操作要求、控制条件、质量标准、频次要求、上下游约束或其它可执行约束；二是该内容能够作为一个相对独立的规则单元被记录和引用；三是该内容能够映射到统一字段体系中，而不是只能作为模糊说明存在。换句话说，并不是 PDF 中所有叙述性文字都会进入规则库，只有具备约束性、可定位性和可结构化表达能力的内容，才会被纳入提取范围。

围绕这一规则单元，当前项目至少维护以下关键信息：规则编号、规则名称、所属大类、所属小项、规则内容、来源文件、来源页码，以及后续 JSON 映射所需的知识类型、子类型、适用范围、触发条件和参数范围等字段。其中，规则编号用于维持全链路唯一标识；规则名称用于表达该条规则的主题；所属大类和所属小项用于知识组织和后续分组维护；来源文件与来源页码用于追溯；规则内容则保留规则的自然语言主表达。也正因为字段定义较完整，后续才能将一条规则从 PDF 原文稳定映射到 Excel 记录，再映射到 JSON 结构。

## 3. PDF规则提取流程

当前项目采用的是“人工识别提取 + 结构化整理 + 多轮校核”的处理方式，而不是直接用程序对 PDF 全文自动抽取规则。具体来看，规则提取首先从阅读原始 PDF 开始。处理人员需要结合项目既定口径，逐页识别哪些原文属于可抽取规则，哪些内容只是背景说明、工艺介绍或非规则性叙述。这个环节的重点不在于把文字抄下来，而在于判断其是否构成一个可独立维护的规则单元。

在识别出候选规则后，下一步是将原文整理为标准化记录，并写入正式主表。这里通常需要完成几项工作：一是提炼规则名称，使其能够准确概括规则主题；二是保留规则内容的自然语言表达，避免过度改写导致原意漂移；三是为规则补充所属大类、所属小项、来源文件和来源页码等字段，确保后续可以回溯到上游文档；四是将后续结构化表达所需的知识类型、子类型、适用范围和参数类字段一并整理进入主表。至此，一条规则才从 PDF 中的自然语言片段，转化为可管理的候选结构化记录。

但主表记录并不等于最终交付结果。本项目中，候选规则进入主总表后，还要继续经历逐项审计、二次收敛、终版审计、规则追溯核对以及 JSON 导出等后续环节，才能成为正式规则库的一部分。也就是说，PDF 提取只是整条链路的起点，而不是终点。项目真正建立起来的能力，不是“从 PDF 里抄出句子”，而是“从 PDF 中识别规则，并把规则稳定送入一条可核验、可维护、可追溯的结构化管理链路”。
